Calibrating an LLM judge for a self-hosted coding agent

The original judge was a coin flip. A better rubric fixed that, and less reasoning made it reliable and 12× faster.

The objective

The Agentic Dev Loop is a coding agent that runs entirely on local models (Ollama behind a LiteLLM proxy, with MLflow and Langfuse for tracking). It plans, writes code, runs frozen acceptance tests in a throwaway container and reviews the result, repeating until the tests pass.

Passing tests only proves the code satisfies the tests, not the whole spec. So a final LLM judge scores every passing build 0–10 on how faithfully it implements the spec. That score goes onto the pull request and into experiment tracking.

The objective was to find out whether that score could be trusted, and to fix it if not.

Method

I built a calibration harness that takes code from 17 past agent runs where it's already known whether the tests passed (11 passing, 6 failing), across three target projects. Each candidate judge scores every sample twice, and the harness measures:

  • AUC: how reliably the judge ranks passing code above failing code on the same target. 0.5 is a coin flip, 1.0 is perfect.
  • The gap between average scores for passing and failing code.
  • Repeat spread: how much the score changes when the judge sees the same code twice.
  • Empty answers: calls where a reasoning model spends its whole token budget thinking and never gives a score.
  • Seconds per call.

Findings

1. The original prompt was a coin flip

The first judge prompt told the model the tests had already passed, then asked it to rate quality. The judge assumed the code was correct and scored nearly everything 9–10. gpt-oss:20b on that prompt scored an AUC of 0.49.

The new rubric doesn't say whether the tests passed. It makes the judge list every requirement in the spec, mark each as met, partial or missing, and deduct fixed points: −2 per missing requirement, −1 per partial one, −1 per mishandled edge case.

2. No model won outright

On the new rubric, gpt-oss:20b and Gemma 4 31B tied at AUC 0.71, for different reasons. In that run gpt-oss was the harshest on bad code, pushing failing builds down to 5.2 on average, but it returned no score on 38% of calls. (A second, identical run later scored failing code at 7.4; see finding 3.) Gemma answered every time and gave almost the same score on repeats, but it rated failing code too kindly (7.6).

A Gemma 4 mixture-of-experts variant ran out of tokens on 28 of 34 calls and was dropped. A community agent-tuned 30B model was the least accurate and the slowest, at nearly 4 minutes per call.

3. Less reasoning made the judge reliable and fast

gpt-oss lets you set how much it reasons before answering: low, medium or high. When no level is set, its chat template uses medium.[1] I ran medium twice (once without setting a level, once setting it explicitly) and low once:

  • Low never came back empty and took about 10 seconds per call. Its median answer used 436 output tokens. It also had the highest AUC (0.80).
  • Medium ran out of tokens on 29–38% of calls and took 107–123 seconds per call. Its median answer used 10,600 tokens, and some hit the 20,000-token cap.
  • The two medium runs disagreed a lot. Same model, prompt and samples: AUC 0.71 vs 0.67, and failing code averaged 5.2 in one run and 7.4 in the other. That's how noisy a 17-sample test is. Low's AUC lead is within that noise; its reliability and speed are not.

4. The catch: low effort squeezes the scores together

AUC only measures ranking. At low effort gpt-oss still ranks failing code below passing code, but failing code averaged 7.4, so the gap between the two is small. What changed in production

  • The judge is gpt-oss:20b at low reasoning effort on the new per-requirement rubric.
  • Each passing build is judged twice and the average is used, because single scores at low effort can swing several points.
  • The pass mark is 9, not 7. A build below 9 still passes and still gets a pull request, but the run and the PR title are flagged for closer review. The judge advises; it doesn't block the build.
  • The judge step went from about 2 minutes to about 20 seconds per run.
  • The reasoning level, repeat count and pass mark are each one config setting, and the calibration harness stays in the repo so the choice can be re-tested.

Caveats

  • The sample is small: 17 builds, only 6 of them failing. Treat this as a first measurement, not a final answer.
  • The pass mark isn't enough on its own. Two failing builds from one target scored 10/10 and 10/8 at low effort, so they'd pass a mark of 9. The flag narrows what a human needs to review; it doesn't replace review.
  • Run-to-run noise is large. Two identical medium runs differed by 2.2 points on the failing-code average. Differences smaller than that between configurations shouldn't be trusted without more runs.
  • AUC is computed per target and then averaged, so a target that's simply harder can't pass for judging skill. With so few failing builds per target, a single sample moves the number.

Takeaways

  1. Measure the judge before trusting its scores. Past runs where you already know whether the tests passed make a free labelled dataset.
  2. Don't tell the judge what you want it to find out. "The tests already passed" was enough to make every model lenient.
  3. More reasoning isn't always better. Check for empty answers and token use, not just scores.
  4. Run it twice before believing a difference. An identical re-run is the cheapest way to learn how noisy your measurement is.
  5. Ranking and the pass mark are separate problems. A judge can rank well while squeezing scores together, so set the pass mark from the data.
