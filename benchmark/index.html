GPU Benchmark Report

RTX PRO 6000 Max-Q (96 GB) vs RTX PRO 5000 (72 GB) — 17 shared models, 4 exclusive, isolated single-GPU containers, Ollama 0.40.6 · plus pooled 6000 + 5000 (168 GB) and 5000 + 3090 (96 GB)

Why I ran this — and where it landed

I had both NVIDIA Blackwell workstation cards in my home lab at the same time and wanted real numbers before committing. The first pass (38 runs, 21 models, 8B to 480B, default settings) favoured the 6000: at the 70B tier the PRO 5000 hit 97% VRAM and fell to 5.9 tok/s while the 6000 held 27.6 tok/s.

A second, tuned pass changed the picture. With flash attention, a q8_0 KV cache and a sensible context, the same 70B model runs at 25.0 tok/s on the 5000 vs 28.2 on the 6000: the earlier gap was a KV cache spilling out of VRAM, not the card. Across the same models the 6000 is about +16% faster, roughly what its extra memory bandwidth predicts.

Decision: I'm returning the RTX PRO 6000. A second PRO 5000 is on order, for 2 × 72 GB = 144 GB. The alternative is to keep running the 5000 with an RTX 3090 (96 GB pooled, measured below) until the 5500 ships.

Benchmark Architecture

Each GPU ran in its own isolated container with exclusive PCI passthrough — no resource contention. Models stored on a shared volume so every model was available to both without re-downloading.

Initial Setup — Two RTX 3090s (48 GB)

Where this started: two 24 GB RTX 3090s in one server and three Ollama lanes. The largest coding model was split by layers across both cards, which pools VRAM but does not make a single request faster: the cards take turns on every token.

Tested Setup — Three Ollama Lanes on the 6000 (96 GB)

While the PRO 6000 was in, I ran three independent Ollama instances on the one card, each serving a different client group. Because they all share one pool of VRAM, what matters is the total resident weight, not the per-lane limit. The lanes are being retired: see No lanes below.

Why three queues, not one? (the reasoning at the time) Ollama processes one forward pass at a time per instance. Three instances give three independent queues — an 8-second 70B generation on the agents lane doesn't block the IDE extension waiting on :11436. NUM_PARALLEL=2 per lane gives 2 concurrent KV cache slots per queue; 3 × 2 = 6 total KV slots across all lanes, all VRAM-permitting. (NUM_PARALLEL was briefly set to 4 during testing but caused VRAM saturation at 96.4/97.9 GB on the 96 GB card — the pre-allocated KV headroom alone exceeded available VRAM with two large models resident.) Since then: NUM_PARALLEL slots inside one server give the same non-blocking behaviour without three configs to keep in sync. See No lanes.

Lane pinning — what broke and what I changed

Observed while moving lanes between cards. Each one changed how the lanes are pinned.

16× slower
A bad pin doesn't fail, it falls back to CPU

A lane was pinned to a card ID its container could no longer see after a card swap. Ollama logged "user overrode visible devices" and kept answering on the CPU, at 14 tok/s against 224 once fixed, for days, with no alert. Fix: lanes resolve their GPU at start and refuse to start without one, and a health guard checks for CPU fallback every 2 minutes.

−5 to −20%
One server across mixed cards uses the slow card

With one Ollama server over 5000 + 3090, models that fit the 5000 still got layers placed on the 3090. Fix: don't pool mismatched cards. Two equal PRO 5000s leave no slow card for a split to wait on.

218 reloads
Model slots must cover the lane's working set

The chatbot lane needs 3 models resident (embeddings, guard, chat) but was capped at 2, causing 218 reloads in 15 minutes. Fix: set MAX_LOADED_MODELS to the lane's working set (3), which stopped the churn.

0 lanes
Where this ends up

Lanes were a workaround for queuing. NUM_PARALLEL and MAX_LOADED_MODELS solve that inside one server, which can place models across cards itself. Fix: one Ollama behind a gateway (below).

The fix · how a lane picks its GPU at start

Plus a health guard every 2 minutes that flags any lane reporting CPU compute, and MAX_LOADED_MODELS sized to each lane's working set. The same start check carries over to the single server below, which must never come up on the CPU either.

What fits where

Total VRAM per setup, split by card, against the size of the models that decide the purchase.

×1.00
6000 + 5000 vs 6000 alone

Ollama keeps a model on one card when it fits, so 25 pooled runs matched the 6000 (×0.95–×1.03). Truly split runs held ×0.87–×1.04: splitting is cheap, spilling to RAM is not. The 150 GB 480B ran only here, at 57.8 tok/s against 9.9 with RAM spill.

−11%
5000 + 3090 vs 5000 alone

The 3090 adds 24 GB of overflow and runs the 77 GB 72B Q8 fully on GPU (13.8 tok/s). The cost is that models that fit the 5000 also get layers on the slower 3090 (936 vs 1,344 GB/s), e.g. gpt-oss:120b drops from 149 to 133 tok/s.

0 / 120
Throttled requests in a 10-minute soak

5000 + 3090 held 207–208 tok/s back to back, with the 5000 peaking at 90 °C and settling at 88 °C. A 250 W cap cost 4% speed and saved 48 W (fan 83% → 69%). The 3090 slowed briefly at a 63 °C core, which points at its GDDR6X memory.

2× PRO 5000: not yet measured

Models that fit one card run at PRO 5000 speed; 72–140 GB models split across two equal cards with no slow card to wait on. It can't hold the 150 GB 480B. I'll rerun the same harness when the second card arrives.

Next — No Lanes: One Ollama Behind a LiteLLM Gateway

Planned, not live yet. Per-card services stay for benchmarking only. Production runs one Ollama over all cards and lets it place models, with a LiteLLM gateway in front.

no auth
The real reason for the gateway

Ollama has no authentication: anything that can reach its port can run, pull or delete models. The gateway puts a key on every client and blocks the admin endpoints.

aliases
Swap models without touching clients

coder → gpt-oss:120b, reviewer → gpt-oss:20b, orchestrator → hermes3:8b, research → llama4:scout, big → the largest model that fits both cards. Changing a model becomes a gateway config change.

1 server
Concurrency without lanes

NUM_PARALLEL lets several agents share one loaded model, and MAX_LOADED_MODELS keeps orchestrator, coder and reviewer resident at once. Three lanes did that by hand, with three configs to keep in sync.

to test
Before the second 5000 goes in

A concurrency test (1, 2 and 4 agents, same and different models) and Qwen3-235B at IQ4_XS (126 GB), the largest ~4-bit model 144 GB can hold.
